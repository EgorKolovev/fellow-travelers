# Контракты фронтенд ↔ бэкенд

Источник истины — [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1). Здесь — общие соглашения, которые в схеме
выражены плохо. Изменения контракта согласуем с фронтом **до** реализации.

Пометки в схеме: `x-stage: pre-mvp` — нужно для pre-MVP, `x-stage: mvp` — появится в MVP
(можно не реализовывать на первом этапе, но форма данных уже зафиксирована).

## 1. Базовое

- База: `https://<host>/api/v1`. Формат — JSON, UTF-8. Поля — `snake_case`.
- Идентификаторы — UUID-строки.
- Отсутствующее значение — `null` (поле присутствует), а не пропуск поля.
- Списки без пагинации на pre-MVP (группа — десятки/сотни участников). Если понадобится — добавим `?cursor=`.

## 2. Аутентификация

Мини-приложение передаёт `Telegram.WebApp.initData` **как есть** в каждом запросе:

```
Authorization: tma <initData>
```

Бэкенд проверяет подпись (HMAC-SHA256 от токена бота) и `auth_date` (не старше 24 ч). Пользователь создаётся
автоматически при первом запросе. Ошибка подписи → `401 UNAUTHORIZED`.

**Телефон.** Мини-приложение телефон не передаёт: пользователь отправляет контакт боту, бот сохраняет его на
бэкенде. Фронт смотрит `GET /me` → `phone`/`has_phone`. Без телефона:
- можно смотреть приглашение;
- нельзя вступить в группу и отправить заявку → `403 PHONE_REQUIRED`. Фронт показывает объяснение и кнопку «Поделиться контактом»
  (`Telegram.WebApp.requestContact()` либо возврат в бота); после этого перезапрашивает `GET /me`.

## 3. Ошибки

Любой ответ 4xx/5xx:

```json
{ "error": { "code": "JOIN_CLOSED", "message": "Вступление в группу закрыто", "details": null } }
```

`message` — человекочитаемый текст на русском, его можно показать как есть. Логика фронта завязывается на `code`.
Для `422 VALIDATION_ERROR` в `details.fields` — словарь `поле → текст ошибки`.

| HTTP | code | Когда |
| --- | --- | --- |
| 422 | `VALIDATION_ERROR` | Неверные/недостающие поля |
| 401 | `UNAUTHORIZED` | Нет или невалиден `initData` |
| 403 | `FORBIDDEN` | Нет прав (не админ группы, не член группы) |
| 403 | `PHONE_REQUIRED` | Действие требует телефона |
| 404 | `NOT_FOUND` | Ресурса нет или он недоступен пользователю |
| 404 | `INVITE_NOT_FOUND` | Неверный код приглашения |
| 409 | `JOIN_CLOSED` | Вступление в группу закрыто |
| 409 | `APPLICATION_LOCKED` | Заявку уже нельзя менять (назначен трансфер на pre-MVP / уже уехал) |
| 409 | `ALREADY_DEPARTED` | Действие недоступно после отметки «Уехал» |
| 409 | `CAPACITY_EXCEEDED` | Заявка/состав не влезает в машину (3 пассажира, 2 места багажа) |
| 409 | `TRIP_IN_USE` | Нельзя удалить рейс — на него ссылаются заявки |
| 409 | `INCOMPATIBLE_TRANSFER` | (MVP) Ручной состав нарушает правила ожидания/вместимости |
| 503 | `FLIGHT_PROVIDER_UNAVAILABLE` | (MVP) Поставщик рейсов недоступен |

## 4. Время и даты

- Моменты времени — ISO 8601 **со смещением**: `"2026-11-12T10:05:00+03:00"`. Бэкенд отдаёт смещение
  часового пояса соответствующего аэропорта (вылет — по аэропорту вылета, прилёт — по аэропорту прилёта).
- У каждой точки (`Location`) есть `timezone` (IANA, `"Europe/Moscow"`) — для расчётов на клиенте
  (обратный отсчёт, «+1 сутки»).
- Даты без времени (даты мероприятия) — `"2026-11-12"`.
- При вводе рейса админ передаёт время **с локальным смещением аэропорта** либо без смещения — тогда бэкенд
  интерпретирует его в таймзоне аэропорта.

## 5. Статусы

**Статус заявки** `ApplicationStatus` (то, что видит участник, CAP-07):

| Значение | UI-текст |
| --- | --- |
| `searching` | Ищем попутчиков |
| `assigned` | Группа назначена (есть трансфер) |
| `solo` | Еду самостоятельно |
| `cancelled` | Участие отменено |

**Отметки** — отдельно от статуса: `at_meeting_point: bool` («Я на месте»), `departed_at: datetime|null` («Уехал»).
После `departed_at != null` любые изменения заявки → `409 ALREADY_DEPARTED`. Исключение (MVP) — отмена
ошибочного «Уехал» в течение 30 минут, см. раздел 10.

**Статус рейса** `TripStatus` (MVP, на pre-MVP всегда `scheduled`): `scheduled`, `delayed`, `departed`,
`landed`, `cancelled`, `unknown`. Источник данных `source`: `manual` | `provider`.

Переходы заявки:

```
           PUT (первая отправка)
                 │
                 ▼
   ┌────────► searching ──(подбор)──► assigned
   │             │  ▲                   │
   │   go-solo   │  │ resume-search     │ go-solo / cancel
   │             ▼  │                   ▼
   │            solo ◄──────────────────┘ (выход из трансфера)
   │             │
   └─ resume ────┤ cancel
                 ▼
             cancelled  (resume-search возвращает в searching)
```

Сервис сам переводит `assigned` → `searching`, если после правки рейса заявка больше не подходит попутчикам,
трансфер расформирован, рейс отменён (MVP) или админ убрал заявку из ручного состава (MVP). Заявка при этом
снова проходит подбор. Пока рейс заявки в статусе `cancelled`, подбор её пропускает: участнику нужно выбрать
другой рейс.

## 6. Ссылки и deep link

- Приглашение: `invite.link` = `https://t.me/<bot>?start=join_<code>` (ведёт в бота). Бот запрашивает телефон,
  если его ещё нет, и показывает кнопку «Вступить в группу» → `https://t.me/<bot>?startapp=join_<code>`.
  Код `invite.code` — 6 символов `[A-Z0-9]`, без регистра, вводится вручную.
- `start_param` мини-приложения (`Telegram.WebApp.initDataUnsafe.start_param`):

| start_param | Что открыть |
| --- | --- |
| `join_<CODE>` | Экран приглашения → `GET /invites/{code}` |
| `event_<uuid>` | Моя поездка в группе → `GET /events/{id}/my-trip` |
| `admin_<uuid>` | Управление группой → `GET /events/{id}/admin/participants` |
| `admin` | Раздел управления: группы, где я админ → `GET /me/events` (фильтр `is_admin`) |
| отсутствует | Список моих групп → `GET /me/events` |

Те же значения используют кнопки бота и (MVP) уведомления. Ссылки вида `https://t.me/<bot>?startapp=<param>`
открывают **Main Mini App** бота — его нужно настроить в BotFather.

## 7. Обновление данных

Push/WebSocket нет. Фронт перезапрашивает данные при открытии экрана и по pull-to-refresh (CAP-07).
Рейсы с `source=provider` сервис обновляет сам по данным поставщика (MVP); правка такого рейса админом
действует до следующего ответа поставщика.

## 8. Основные экраны → эндпоинты

| Экран | Запросы |
| --- | --- |
| Старт / профиль | `GET /me` |
| Мои группы | `GET /me/events` |
| Создание / настройка группы | `POST /events`, `PATCH /events/{id}`, `GET /events/{id}/invite` |
| Приглашение | `GET /invites/{code}`, `POST /invites/{code}/join` |
| Рейсы группы (админ) | `GET/POST /events/{id}/trips`, `PATCH/DELETE /trips/{id}`, `GET /locations` |
| Заявка | `GET /events/{id}/trips`, `GET /flights/search` (MVP), `GET/PUT /events/{id}/my-application` |
| Моя поездка | `GET /events/{id}/my-trip`, действия `POST /events/{id}/my-application/{go-solo,resume-search,cancel}`, `PUT .../marks` |
| Управление: участники | `GET /events/{id}/admin/participants`, `GET /events/{id}/admin/transfers` |
| Управление: история | `GET /events/{id}/admin/history?limit=&before_seq=` |
| (MVP) Табло, правка составов | `GET /events/{id}/admin/board`, `POST /events/{id}/admin/transfers`, `PUT /events/{id}/admin/transfers/{tid}/members`, `POST .../admin/applications/{aid}/departed`, `POST .../admin/transfers/{tid}/departed` |

## 9. Роли и доступ

- Создатель группы — её админ (`is_admin=true`). Участником он **не становится автоматически**
  (`is_participant=false`): если едет сам, вступает по своему же приглашению и заполняет заявку.
- Пользователь, который не админ и не участник группы, получает `404 NOT_FOUND` на любые её ресурсы —
  существование группы не раскрываем.
- Участник, который пытается выполнить действие админа, получает `403 FORBIDDEN`.
- `PATCH` различает «поле не передано» и `null`: `null` допустим только для `pickup_point` (сброс —
  посадка там же, где сбор) и `chat_url` (удалить ссылку).
- Во входных телах лишние поля запрещены → `422 VALIDATION_ERROR` («Лишнее поле»).

## 10. Заявка: поведение, важное для UI

- `PUT /my-application` принимает необязательное `seek_companions`. `false` — заявка сохраняется
  сразу в `solo`, подбор не запускается («Не искать попутчиков», например компания больше двух человек).
  `true` — заявка переходит в `searching` (в том числе из `solo`/`cancelled`) и запускается подбор.
  Без поля — поведение ниже.
- Подать заявку может только **участник** группы. Админ без участия получает `403 FORBIDDEN` —
  UI предлагает вступить по своему приглашению.
- Ответ на `PUT /my-application` и на действия уже отражает результат подбора: если попутчики нашлись
  сразу, придёт `status: "assigned"` и `transfer_id`.
- Новая заявка может попасть и в уже собранный трансфер, если в нём есть свободное место, никто ещё не
  уехал и состав собран автоматически. Поэтому у участников трансфера может появиться третий попутчик.
- `PUT` при статусе `assigned` (MVP) меняет заявку. Если попутчики с новыми данными по-прежнему подходят
  и места хватает, заявка остаётся в трансфере. Иначе она выходит из трансфера, остальные остаются вместе,
  сервис ищет им замену, а изменённая заявка снова проходит подбор. Ответ уже показывает итог:
  тот же `transfer_id`, новый или `searching`. `409 APPLICATION_LOCKED` на `PUT` больше не возвращается.
- `PUT` при статусе `solo` меняет данные, но статус остаётся `solo`; при `cancelled` — заявка
  возвращается в `searching`.
- Если из трансфера вышел один из двоих, трансфер расформировывается, оставшийся снова ищет попутчиков.
  Если из троих — двое остаются вместе, а сервис ищет им третьего среди заявок в поиске.
  Если оставшийся уже отметил «Уехал», он получает статус `solo`, а не `searching`.
- После `PATCH /trips/{id}` с новым временем прибытия или аэропортом трансферы группы пересчитываются в фоне
  за несколько секунд. Из трансфера выходит только заявка, которой новое время больше не подходит;
  задержка в пределах ожидания состав не меняет. Экраны видят результат при следующем запросе.
- «Уехал» не меняет статус заявки. В течение 30 минут после отметки участник может её отменить:
  `PUT .../marks` с `departed=false` (MVP). Если прежний трансфер ещё активен, заявка возвращается в него;
  если его уже нет, заявка получает `searching` и снова проходит подбор; `solo` остаётся `solo`.
  Позже 30 минут и при любых других изменениях после отъезда → `409 ALREADY_DEPARTED`.
- Админ может отметить отъезд заявки или всего трансфера (MVP). Отметка админа равна отметке участника,
  её тоже можно отменить в течение 30 минут.
- `GET /my-trip` (MVP): `meeting_map_url` открывает место сбора в Яндекс Картах, `taxi.yandex_go_url` —
  заказ в Яндекс Go из точки посадки в точку назначения. Обе ссылки `null`, если у нужных точек нет
  координат. Координаты админ передаёт в `Point.lat` и `Point.lon` вместе: одна без другой → 422.
- Изменение мест сбора, посадки, назначения или инструкции (MVP) трансферы не пересчитывает: точки общие
  для всей группы.
- Повторные `go-solo`, `resume-search`, `departed=true` идемпотентны — отвечают `200` с текущим состоянием.

## 11. История

`GET /events/{id}/admin/history` — только админу группы. Записи идут от новых к старым, страница до `limit`
(по умолчанию 100, максимум 200). Следующая страница — `?before_seq=<next_before_seq>`; `null` — дальше записей нет.
История хранится вместе с группой и удаляется вместе с ней; телефонов и username в ней нет.

`actor_kind`: `participant` — сам участник, `admin` — создатель группы, `system` — сервис (подбор и пересчёт).
`reason` объясняет, почему произошло изменение, и может быть `null`.

| `action` | Когда | `details` |
| --- | --- | --- |
| `application_submitted` | Первая отправка заявки | `status` |
| `application_updated` | Повторный `PUT` | `changed_fields`, `status` |
| `status_changed` | Смена статуса вне трансфера (go-solo, resume-search, cancel) | `from_status`, `to_status` |
| `marks_changed` | «Я на месте» или «Уехал» | `at_meeting_point`, `departed` |
| `transfer_created` | Собран новый трансфер | `application_ids` |
| `transfer_joined` | Заявка дополнила трансфер | — |
| `transfer_left` | Заявка вышла из трансфера, в том числе при расформировании | `from_status`, `to_status` |
| `transfer_dissolved` | В трансфере осталось меньше двух заявок | `application_ids` — кто остался |
| `transfer_departed` | Все участники уехали | — |
| `trip_updated` | Админ исправил рейс или пришли новые данные поставщика (`actor_kind=system`, `reason=provider_update`) | `changed_fields`, `effective_arrival_before`, `effective_arrival_after` |

Причины MVP: `application_changed` — заявка вышла из трансфера после правки участником; `departure_undone` —
возврат в трансфер после отмены «Уехал»; `flight_cancelled` — выход из трансфера из-за отмены рейса;
`admin_edit` — ручной состав и отметки админа.

Состав любого трансфера восстанавливается по записям: `transfer_created.details.application_ids`, плюс
`transfer_joined`, минус `transfer_left`.

Для трансферов, собранных до появления истории, запись `transfer_created` добавлена при обновлении: `reason`
равен `null`, `occurred_at` — время создания трансфера, `seq` — момент обновления. Остальных событий до
обновления в истории нет.

## 12. Уведомления (MVP)

Сервис пишет участникам в Telegram от имени бота. Кнопка в сообщении открывает мини-приложение с
`start_param=event_<uuid>` (раздел 6). Сообщение приходит, если участник уже писал боту и не заблокировал его.

| Событие | Кому |
| --- | --- |
| Трансфер собран, дополнен, изменён или расформирован | Участникам этого трансфера, включая вышедшего и нового |
| Изменились места сбора, посадки, назначения или инструкция | Всем участникам группы с заявкой не в статусе `cancelled` |
| Расчётное прибытие рейса сдвинулось на 15 минут и больше от последнего сообщённого значения | Пассажирам рейса и их попутчикам по трансферу (попутчику — «рейс попутчика») |
| Рейс отменён | Пассажирам рейса. Попутчики получают сообщение об изменении состава, когда сервис пересоберёт трансфер |

Своё действие участнику не сообщается. Админу копия не отправляется. Одно действие сервиса даёт одному
человеку не больше одного сообщения; следствие изменения, обработанное позже (например, пересборка трансфера
после сдвига рейса), может дать ещё одно. Сообщение уходит примерно через 30 секунд; изменения, пришедшие до
отправки, склеиваются в одно («в поездке несколько изменений»). По одной группе человек получает не больше
6 сообщений в час, следующее приходит после окончания окна и включает всё накопившееся. Уехавшим сообщения о составе и точках не отправляются. В тексте нет
телефонов: контакты попутчиков открываются в мини-приложении. Название группы в тексте очищается от ссылок,
упоминаний и телефонов и обрезается до 60 символов.

## 13. Удаление данных (MVP)

Через 7 суток после самого позднего из моментов — конца последнего дня мероприятия (`ends_on`), последней
отметки «Уехал», создания группы и её последней правки — группа удаляется вместе с участием, заявками, трансферами, рейсами и историей. Профиль и
телефон пользователя остаются. После удаления код приглашения отвечает `404 INVITE_NOT_FOUND`, ссылки на
группу — `404 NOT_FOUND`. Удаление включается настройкой сервиса; пока она выключена, группы хранятся.
